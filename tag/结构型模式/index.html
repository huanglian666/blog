结构型模式概述

结构型模式（Structural Pattern）关注类和对象如何组合成更大的结构，重点解决功能扩展、接口适配和对象组合等问题。它们描述的不是"怎么创建对象"，而是"对象之间如何搭接"，往往通过继承或组合的方式将多个类/对象组织起来，形成更灵活、更易扩展的结构。

GoF 结构型模式包括代理、适配器、装饰者、桥接、外观、组合和享元 7 种。它们各自解决的问题可以概括如下：

模式 核心问题 一句话概括
代理模式 如何在不改动目标对象的前提下控制对它的访问 中间加一层代理，访问前/后做增强
适配器模式 已有接口与目标接口不匹配怎么办 转接头，把旧接口包装成需要的接口
装饰者模式 如何动态地为对象增加功能而不使用继承 一层一层"包"上去，灵活叠加职责
桥接模式 两个独立变化的维度如何避免类爆炸 用组合桥接两个维度，各自独立扩展
外观模式 子系统太复杂，调用方如何简化交互 提供一个统一的入口封装复杂子系统
组合模式 树形结构中叶子与容器如何统一处理 让单个对象与组合对象使用一致的接口
享元模式 大量细粒度对象如何节省内存 共享内部状态，减少重复对象

代理模式

1. 概述

定义：由于某些原因需要给某对象提供一个代理以控制对该对象的访问。这时，访问对象不适合或者不能直接引用目标对象，代理对象作为访问对象和目标对象之间的中介。

Java 中的代理按照代理类生成时机不同又分为静态代理和动态代理：静态代理的代理类在编译期就生成，而动态代理的代理类则是在 Java 运行时动态生成。动态代理又有 JDK 代理和 CGLIB 代理两种。

适配器模式

1. 概述

如果去欧洲国家旅游的话，他们的插座是欧洲标准（如下图最左边），而我们使用的插头是国标（如下图最右边）。因此我们的笔记本电脑、手机在当地不能直接充电。所以就需要一个插座转换器：转换器第 1 面插入当地的插座，第 2 面供我们充电，这样使得我们的插头在当地能使用。生活中这样的例子很多，手机充电器（将 220V 转换为 5V 的电压）、读卡器等，其实都使用到了适配器模式。

定义：将一个类的接口转换成客户希望的另外一个接口，使得原本由于接口不兼容而不能一起工作的那些类能一起工作。

适配器模式分为类适配器模式和对象适配器模式：前者的类之间耦合度比后者高，且要求程序员了解现有组件库中的相关组件的内部结构，所以应用相对较少些。

装饰者模式

1. 概述

我们先来看一个快餐店的例子。

快餐店有炒面、炒饭这些快餐，可以额外附加鸡蛋、火腿、培根这些配菜，当然加配菜需要额外加钱，每个配菜的价钱通常不太一样，那么计算总价就会显得比较麻烦。

如果用继承的方式实现"各种快餐 + 各种配菜"的组合，会存在以下问题：

  • 扩展性不好：如果要再加一种配料（火腿肠），就需要给 FriedRice 和 FriedNoodles 分别定义一个子类；如果要新增一个快餐品类（炒河粉），就需要定义更多的子类；
  • 产生过多的子类：快餐品类数 × 配菜数的组合都要靠子类表达，子类数目呈爆炸性增长。

桥接模式

1. 概述

现在有一个需求：需要创建不同的图形，并且每个图形都有可能会有不同的颜色。我们可以利用继承的方式来设计类的关系：

我们可以发现有很多的类：假如我们再增加一个形状或再增加一种颜色，就需要创建更多的类。

试想，在一个有多种可能变化的维度的系统中，用继承方式会造成类爆炸，扩展起来不灵活：每次在一个维度上新增一个具体实现，都要在另一个维度上增加多个子类。为了更灵活地设计系统，我们此时可以考虑使用桥接模式。

定义：将抽象与实现分离，使它们可以独立变化。它是用组合关系代替继承关系来实现，从而降低了抽象和实现这两个可变维度的耦合度。

外观模式

1. 概述

有些人可能炒过股票，但其实大部分人都不太懂，在没有足够证券知识的情况下做股票是很容易亏钱的。刚开始炒股肯定都会想：如果有个懂行的帮手就好。其实基金就是个好帮手——支付宝里就有许多的基金，它将投资者分散的资金集中起来，交由专业的经理人进行管理，投资于股票、债券、外汇等领域，而基金投资的收益归持有者所有，管理机构收取一定比例的托管管理费用。投资者不需要懂每只股票，只需要"买基金"这一个入口。

定义：外观模式（Facade，又名门面模式）是一种通过为多个复杂的子系统提供一个一致的接口，而使这些子系统更加容易被访问的模式。该模式对外有一个统一接口，外部应用程序不用关心内部子系统的具体细节，这样会大大降低应用程序的复杂度，提高程序的可维护性。

1. 概述

享元模式

1. 概述

定义：运用共享技术来有效地支持大量细粒度对象的复用。它通过共享已经存在的对象来大幅度减少需要创建的对象数量、避免大量相似对象的开销，从而提高系统资源的利用率。

一句话理解：如果一万个对象里其实只有少数几种"本质不同的样子"，那就只创建这几种，其他地方全部共享引用，用的时候再把"随环境变化的部分"临时传进去。

2. 结构

享元（Flyweight）模式中存在以下两种状态：

  1. 内部状态：即不会随着环境的改变而改变的可共享部分；
  2. 外部状态：指随环境改变而改变的不可以共享的部分。享元模式的实现要领就是区分应用中的这两种状态，并将外部状态外部化。
